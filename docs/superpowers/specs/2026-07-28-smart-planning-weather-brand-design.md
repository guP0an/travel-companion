# 丸玩智能规划、天气幕布与品牌统一设计

## 目标

把当前“一句话直接生成”的流程改成真正会补问必要信息的旅行管家，并让有真实预报的每日行程显示已确认的天气幕布；同时将用户可见品牌名从“丸丸”统一为“丸玩”，并让每趟行程拥有独立账本。

成功标准：

- 用户输入“这周末去日本”时，系统先解析已有信息，再一次性追问缺少的必要信息。
- 跨境行程至少确认出发城市、具体目的城市、出发日期/天数和同行人；预算与偏好可跳过。
- 相对日期按用户浏览器时区解析；“周末”与页面天数冲突时必须确认，不能猜。
- 信息齐全后才生成行程，并保证每天都有连续的 `YYYY-MM-DD` 日期。
- 预报范围内每天显示天气、最低/最高温和对应的横向天气幕布；超出预报范围时整块不显示。
- 用户可见网页、小程序、AI 管家文案和产品文档统一使用“丸玩”。
- `wanwantrip.online`、Cookie、数据库、邮箱后缀、包名和仓库名等内部技术标识保持不变。
- 从日本行程打开账本时只显示日本账目；香港旧账不再混入当前行程。
- 账本目录按已保存行程展示总额，无法可靠判断归属的旧账进入“历史未归档”，可由用户归档到某趟行程。

## 方案选择

### 采用：两阶段追问

第一阶段只理解需求和检查缺失字段，返回“需要补充”或“可以生成”；第二阶段才调用现有行程生成流程。这样能明确控制必问项，也能让用户连续补充两到三轮。

### 不采用：只加强提示词

当前接口强制模型立即返回完整行程 JSON，提示词再强也无法让前端接住追问结果，而且模型仍可能省略日期。

### 不采用：微调模型

问题来自交互协议和确定性校验缺失，不是旅行知识不足。微调成本高，也不能替代日期、必填字段和天气边界校验。

## 架构与数据流

### 1. 需求理解

新增独立的 `intake` 请求，输入包括：

- 用户原话；
- 页面已有天数和节奏；
- 用户浏览器的当前日期与时区；
- 上一轮解析草稿及用户补充内容。

服务端以 JSON 返回两种结果之一：

```text
needs_input -> questions + draft
ready       -> normalizedInput
```

必要字段规则由服务端确定，不交给模型自由决定：

- 跨境：出发城市必填；
- 目的地只有国家时：具体城市或区域必填；
- 出发日期或可确定的相对日期必填；
- 行程天数与日期表达冲突时必须确认；
- 同行人必填；
- 预算和兴趣是可选项，缺失时使用页面展示的默认值。

前端在原规划表单内显示丸玩的追问气泡，用户继续在同一输入框回答。最多三轮；仍不完整时明确列出未补字段，不生成残缺行程。

### 2. 行程生成与日期保证

`ready` 后沿用现有 `plan` 请求和 JSON 行程结构。服务端根据已确认的出发日期按天连续写入 `day.date`，不再依赖模型自觉填写；校验器拒绝天数不一致或非法日期。

默认 DeepSeek 模型名更新为 `deepseek-v4-flash`，但保留 `DEEPSEEK_MODEL` 环境变量覆盖能力。无需训练或增加新模型服务。

### 3. 天气幕布

现有 Open-Meteo 查询继续作为唯一日常天气来源。`DayWeather` 增加最大风速，天气代码映射为：

- 晴：暖色光晕缓慢呼吸；
- 多云/阴：浅色云层错速漂移；
- 小雨/中雨/大雨：整行细雨，落点、长度、透明度、速度和起始时间不规则；强度只改变密度与速度；
- 小雪/中雪/大雪：回到第一版的浅色细小雪粒/圆点，以密度和速度区分强度，不使用摄影图、复杂雪花晶体或深色底图；
- 大风：细弧形风线与少量叶片横向掠过。

幕布铺满每日标题行，日期、天气文字、温度和行程主题保持可读。动画仅用 CSS/SVG，不增加依赖；启用 `prefers-reduced-motion` 时停止位移动画。

没有对应日期天气时不渲染幕布和占位；天气接口失败时保留普通每日标题，不影响行程正文。

## 品牌统一

以下内容改为“丸玩”：

- 网页标题、页头页脚、按钮、提示语、无障碍标签和导出文件名；
- AI 系统角色、生成文案和错误提示；
- 微信小程序可见名称与说明；
- 产品文档中的品牌称呼。

以下内容不改：

- 域名 `wanwantrip.online`；
- `wanwan_*` Cookie、本地存储键和内部邮箱后缀；
- Supabase 项目名、仓库名、包名和已有数据库结构。

## 行程独立账本

数据库已经存在 `expenses.itinerary_id`，本次直接启用该字段，不新增账本表：

- `App` 保存当前行程的数据库 ID；从“我的行程”打开时保留整条 `SavedItinerary`，不再只取出 `plan`。
- 从当前行程点击“账本”时，传入当前 `itinerary_id`，账目查询、总额、记账、查重和删除都限定在该行程。
- 尚未保存的生成行程第一次打开账本时只保存一次，以取得稳定的行程 ID；页面提示“已保存本次行程用于记账”。
- 票据在行程 ID 尚未生成前只保留为待记账项目；行程保存后再写入该行程账本，不能继续产生无归属的新账。
- 账本内可返回“账本目录”。目录列出用户已保存行程的目的地、日期和消费总额，点击后进入该趟账本。
- 历史 `itinerary_id is null` 的消费统一放入“历史未归档”。不根据备注自动猜测归属；用户可选择香港等已有行程完成归档。

不采用按目的地文字过滤，因为同一城市可能有多次旅行；不采用删除或自动迁移旧账，因为会造成数据误归或丢失。

## 错误处理

- 需求理解失败：保留用户输入，显示可重试提示，不直接生成。
- 日期无法唯一确定：追问具体日期。
- 用户拒绝提供出发城市：可以继续浏览表单，但跨境行程不生成。
- 行程模型漏字段：服务端进行一次现有修复流程；仍不合法则返回友好错误。
- 天气或地理编码失败：静默降级为无天气幕布，不伪造天气。
- 当前行程保存失败：不打开空账本，保留页面并提示重试。
- 历史账目归档失败：原账目保持未归档，不丢失凭证。

## 测试与验收

- 单元测试：相对周末日期、跨境必问字段、国家级目的地、天数冲突和连续日期。
- 单元测试：WMO 天气强度、风速映射和无天气时不渲染。
- API 测试：`intake` 两种响应、输入长度和非法草稿校验。
- 数据测试：每次新增、查询和查重消费都带 `itinerary_id`；账本目录按行程汇总；未归档旧账不会混入当前行程。
- 回归测试：从已保存行程打开时保留行程 ID；未保存行程打开账本只创建一份行程记录。
- 回归测试：原有明确输入仍可生成，修改行程、票据、收藏和分享不受影响。
- 品牌检查：运行时代码和小程序用户可见文案不再出现“丸丸”。
- 发布门槛：`pnpm test`、`pnpm build`、375/390/430px 页面检查。
- 线上验收：用“这周末去日本”确认系统先追问；补齐信息后确认每日日期、温度和天气幕布，并确认一个月后的行程不显示天气。
