## 1. 背景与一句话定位

旅游规划的痛不在「查不到信息」，而在信息散、路线难排、选择瘫痪、临场易变。
大平台（携程/马蜂窝/小红书）做的是**冷冰冰的信息聚合**，给你一堆素材，最后还是你自己累死累活地排。

**一句话定位：**
> 一个**陪你走完每一程、还记得你走过哪儿**的 AI 旅行管家——**行前帮你排，行中陪你走，行后替你记**。给你的不是行程清单，是一个带审美和态度、有声音、懂你的旅伴。

差异化 = 「态度 + 懂你 + 全程陪伴 + 记住你」，这是大平台和通用 AI 都给不了的——通用 AI 只是行前问一下就走，我们陪完整程并沉淀成记忆。完整的差异化与护城河论证见 [08-travel-lifecycle-and-moat.md](08-travel-lifecycle-and-moat.md)，这是本产品的 IP 内核。

## 2. 目标用户 & 核心场景

- **用户**：会自由行、但懒得做攻略、有点审美要求的年轻人（第一个用户 = lord 自己）。
- **核心场景**：
  > 我下个月想去 ×× 玩 N 天，预算大概 ×× ，我不爱早起、讨厌排队、爱吃。
  > → 5 秒后拿到一份排好路线、带管家口吻点评的每日行程，能直接照着走。

## 3. MVP 范围（关键：做什么 / 不做什么）

### ✅ 做（v0.1 网页原型）
1. 自由文本描述目的地/需求 + 天数 + 节奏；可上传票务/酒店截图作为排程约束。
2. 生成一份**带性格的每日行程**：按 Day 1…N，每天分上午/下午/晚上，含景点、餐饮、交通提示 + 管家口吻点评。
3. 结果可一句话修改、手动编辑、收藏到云端，并导出 PNG 分享卡。
4. 用 Supabase 提供轻量账号、跨设备行程、账本、打卡点评与照片存储。
5. 用真实天气、地图入口与可遇景观提示增强出行可用性。
6. 界面好看（这是「艺术品」雏形，体现 lord 的前端审美）。

### ❌ 暂不做（防止范围爆炸）
- 不做支付（第 0 级免费验证）。
- 不做小程序/App（验证 OK 再说）。
- 不做实时机票/酒店价格与余票交易。
- 不做地图实时导航、记忆地图、论坛和语音陪伴。

## 4. 功能详述

### 4.1 输入
| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| 目的地/需求 | 自由文本 | 是* | 城市/国家和旅行要求；上传预订截图时可由票据推断 |
| 天数 | 数字 | 是 | 1–15 天 |
| 节奏 | 单选 | 是 | 紧凑 / 适中 / 溜达 |
| 票务/酒店截图 | 图片 | 否 | OCR 后提取日期、交通、酒店和价格，可编辑 |
| 预算/同行人/偏好 | 自由文本 | 否 | 当前写在需求中；下一里程碑改为提问引导式收集 |

### 4.2 输出（核心体验）
- 顶部：一句管家式开场白（带性格，例：「京都这季节正好，我给您排得松快些，早上不催您起床。」）
- 主体：Day 1 … Day N，每天 = 上午 / 下午 / 晚上 三段
  - 每段：地点名 + 一句为什么推荐 + 交通/时间提示
  - 关键处带「管家提醒」（如：「这家店 12 点后排长队，咱们 11 点到。」）
- 底部：一键复制全文 / 保存本程

### 4.3 历史
- 登录后保存到 Supabase，跨设备列表可点开重看。

## 5. 信息架构 / 页面

- **P1 首页/输入页**：丸丸品牌 + 自由文本 + 天数/节奏 + 票务截图 + 生成按钮。

（v0.1 可以单页内切换状态，不必做路由。）

## 6. 技术方案（v0.1）

- **前端**：React + Vite + TypeScript。
- **样式**：TailwindCSS v4。
- **行程生成**：前端 → **serverless 代理函数（藏 API Key）** → DeepSeek API（OpenAI 兼容），返回结构化行程 JSON，前端渲染。
  - ⚠️ API Key 绝不入前端（F12 即可被盗刷）。必须经后端代理。详见 `04-architecture-and-data-model.md`。
  - 当前已接真 API；`src/mock/kyoto.ts` 仅保留为前端初始样例，下一轮应移除首屏原型残留。
- **后端**：极轻的 serverless 函数（Vercel Functions / Cloudflare Workers）做 DeepSeek 代理（藏 Key）；账号与数据库交给 **Supabase**（BaaS）。
- **账号与存储**：**Supabase Auth**（登录）+ **Postgres**（行程/偏好云端存储，跨设备）。前端用 anon key + 行级安全（RLS）直连；DeepSeek key 仍只在 serverless 代理。详见 [04 §7](04-architecture-and-data-model.md)。
- **部署**：Vercel（Vite 静态前端 + `api/ai.ts` serverless 函数）。

---

## 7. 数据与隐私

- 使用 Supabase Auth；行程、账本、打卡和照片存储在用户自己的云端数据空间，并通过 RLS 隔离。
- DeepSeek 只通过服务端代理调用，服务端 Key 不进入前端；用户的规划文本和 OCR 结果会发送给模型。
- 打卡照片当前使用公开读取的 Storage URL，正式扩大内测前需要复核隐私提示与上传限制。

## 8. 成功指标（怎么算「验证通过」）

第 0 级只看三个信号，**不看收入**：
1. **可用**：lord 自己用它规划了至少 1 次真实旅行，且觉得「比自己排省事」。
2. **想转发**：给 ≥5 个朋友用，有人主动说「这个不错」或转给别人。
3. **回头**：有人用了不止一次。

三个里中 ≥2 个 → 进入第 1 级（上小程序、注册个体户、接支付）。

## 10. 风险 & 对策

| 风险 | 对策 |
|------|------|
| 行程质量不稳定（AI 瞎编景点） | prompt 里强调真实性；后期接真实 POI 数据 |
| 和大平台同质化 | 死磕「性格 + 懂你」，不拼信息全 |
| 范围爆炸做不完 | 严守第 3 节「不做」清单 |
| 个人主体小程序不能收款 | 验证 OK 后注册个体工商户再上小程序 |
